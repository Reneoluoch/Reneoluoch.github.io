🔹 Project: Enabling Just-In-Time (JIT) VM Access

Summary

In this lab, I focused on strengthening privileged access management for Azure virtual machines by implementing Just-In-Time (JIT) access. JIT ensures that management ports such as RDP (3389) remain closed by default and only open temporarily when explicitly requested by an administrator. This reduces exposure to brute-force attacks and unauthorized logins.

Detailed Activities:

  • Accessed the Azure Virtual Machines blade and selected myVM, previously deployed in Lab 08.
  • Navigated to Configuration → Just-In-Time VM Access and enabled JIT via Microsoft Defender for Cloud.
  • Reviewed and configured the default JIT policy, which protected TCP port 3389 (RDP) with a maximum 3-hour session.
  • Learned how to customize JIT rules by adding new ports or adjusting IP restrictions.
  • Saved the JIT configuration, ensuring inbound traffic was now locked down by default.

Validation:

  • Tested the configuration by navigating to Connect → Request Access on the VM.
  • Verified that JIT required explicit access requests, which temporarily opened RDP for the administrator’s IP address.
  • Confirmed that ports closed automatically once the access window expired.

Outcome:

JIT access was successfully implemented and tested. This security measure reduced the VM’s attack surface while ensuring administrators could still securely perform maintenance tasks when required. The exercise demonstrated best practices for time-bound privileged access in cloud environments.

CloudGoat IAM Privilege Escalation by Rollback Scenario

Author: Rene Oluoch
Reg No: CS-CNS09-25030
Assignment: 1

🔹 Introduction

This project explores how misconfigurations in AWS IAM can lead to privilege escalation attacks, using the iam_privesc_by_rollback scenario in CloudGoat. The exercise was conducted in a controlled AWS environment using Kali Linux, with the IAM user Raynor as the starting point. The goal was to demonstrate how attackers can exploit SetDefaultPolicyVersion permissions to escalate from limited user access to full administrative control.

🔹 Task 1: Initial Setup

Prepared a Kali Linux VM with AWS CLI installed and configured using personal AWS credentials. Verified setup with aws sts get-caller-identity and ensured CloudGoat requirements (Terraform, jq) were installed. This laid the foundation for deploying the vulnerable environment.

🔹 Task 2: Accessing CloudGoat

Cloned the CloudGoat repository from GitHub and configured it with AWS credentials. Verified functionality with cloudgoat help and cloudgoat list, confirming readiness to deploy scenarios.

🔹 Task 3: Understanding the Scenario

The scenario deployed an IAM user Raynor with a policy containing multiple versions. The exploit path relied on the SetDefaultPolicyVersion permission, allowing rollback to an older version (v3) that granted full admin access.

🔹 Task 4: Starting the Scenario

Deployed the iam_privesc_by_rollback scenario. Configured AWS CLI with Raynor’s credentials and verified limited access by running IAM commands. At this stage, Raynor only had restricted permissions.

🔹 Task 5: Exploring Initial Configuration

Listed attached policies and their versions using aws iam list-policy-versions. Found that the default policy was restrictive but older versions contained admin-level privileges. Confirmed that Raynor had iam:SetDefaultPolicyVersion rights.

🔹 Task 6: Performing Privilege Escalation

Executed privilege escalation by rolling back to version 3 of the policy with aws iam set-default-policy-version. This successfully elevated Raynor from limited permissions to full administrator rights.

🔹 Task 7: Verification

Verified escalation by performing admin-level actions, such as creating a new IAM user (test-admin), listing roles, and attaching policies. Demonstrated stealth by reverting to the restrictive policy version afterward, simulating attacker cover-up tactics.

🔹 Task 8: Reflection and Analysis

Highlighted that allowing users to set default policy versions poses a severe security risk, especially when older permissive versions exist. Emphasized the need for least privilege, strict policy version management, logging, and monitoring of IAM changes to prevent misuse.

🔹 Conclusion

The scenario showed how IAM misconfigurations can enable privilege escalation and stealthy exploitation. Key lessons included the importance of removing outdated policy versions, enforcing least privilege, and auditing IAM activities to secure AWS environments against rollback-based attacks.
